# План пилота

## 1. Неопределённости, которые проверяет пилот

| №  | Неопределённость                                                      | Критично для чего       | Как проверяем                                                            |
|----|-----------------------------------------------------------------------|-------------------------|--------------------------------------------------------------------------|
| U1 | Даёт ли модель прирост **Precision@K** над baseline при одинаковом K? | Весь эффект             | Слепое сравнение очередей при одинаковом K по единой экспертной разметке |
| U2 | Насколько реально сокращается время разбора?                          | Основная статья эффекта | Замер в пилотной группе vs контрольной                                   |
| U3 | Снижается ли доля ложных блокировок?                                  | Вторая статья эффекта   | Сравнение приостановок и жалоб                                           |
| U4 | Достаточно ли контрольной выборки для честной оценки?                 | Риск ложного оптимизма  | Сравнение метрик на контрольной vs разобранной очереди                   |
| U5 | Выдерживает ли инфраструктура поток?                                  | TCO                     | Нагрузочное тестирование                                                 |

## 2. Дизайн пилота

- Длительность: **6 месяцев**.
- Скоуп: флагман, только CatBoost + правила (без графа).
- **Разметка контрольной выборки: 2 000 операций** (соответствует смете Task4/01).
- Пилотная группа (модель + правила) vs контрольная (правила + сумма). Сотрудники не знают, из какой группы операция.

## 3. Определение Precision@K (единое для всех артефактов)

**Precision@K** — доля операций в верхушке очереди (top-K), по которым эксперт финмониторинга по действующей процедуре
**нашёл основания для эскалации на расследование или для отказа в проведении операции**.

**Как считается на пилоте:**

1. Берём top-K из пилотной очереди и top-K из контрольной при **одинаковом K**.
2. Формируем объединённый набор операций (с пересечениями, если они есть).
3. Независимый эксперт размечает каждую операцию по вопросу «есть ли основания для эскалации или отказа» — **не зная, из
   какой очереди операция** (слепой дизайн).
4. Precision@K = доля операций с основаниями в top-K каждой очереди.
5. Разница между очередями при одинаковом K и одной разметке — эффект модели.

**Что не используется как Precision@K:**

- Формально подтверждённые схемы — единицы, появляются с лагом в месяцы. Отслеживаются **отдельно** как lagging-метрика
  (см. раздел 6).
- Число эскалаций, открытых правилами — это не качество модели.
- Средний скор — не отражает ранжирование.

## 4. Критерии успеха

| Критерий                                   | Порог                                                       | Откуда порог                                 |
|--------------------------------------------|-------------------------------------------------------------|----------------------------------------------|
| **Precision@K** (по определению раздела 3) | Выше baseline на ≥ 5 п.п. при одинаковом K и одной разметке | Ниже 5 п.п. — в пределах шума; **критичный** |
| Сокращение времени разбора                 | ≥ 10% (цель 15%)                                            | Ниже 10% — эффект не перекрывает TCO         |
| Снижение приостановок                      | ≥ 5% (цель 10%)                                             | Ниже 5% — вторая статья эффекта не работает  |
| Доля фолбэков                              | ≤ 20%                                                       | Выше — ручной контур перегружен              |
| Задержка inference                         | ≤ 200 мс p95                                                | Требование к UX                              |

## 5. Guardrails

| Guardrail                            | Порог                              | При нарушении                       |
|--------------------------------------|------------------------------------|-------------------------------------|
| Доля пропущенных подтверждённых схем | Не растёт vs контрольная (lagging) | Стоп-пилот, разбор                  |
| Время разбора                        | Не растёт                          | Стоп-пилот, пересмотр UI            |
| Жалобы                               | Не растут                          | Разбор каждой, корректировка порога |
| Нагрузка на сотрудника (опрос)       | Не растёт                          | Корректировка                       |
| Доступность сервиса                  | ≥ 99,5%                            | Инцидент, фолбэк на правила         |

## 6. Lagging-метрика: подтверждённые схемы

Отслеживается отдельно, **не входит в критерии успеха пилота** из-за лага в месяцы:

| Метрика                                              | Как                         | Зачем                                          |
|------------------------------------------------------|-----------------------------|------------------------------------------------|
| Число подтверждённых схем в top-K пилота vs контроля | По завершении расследований | Длинный горизонт: подтверждает реальный эффект |
| Доля подтверждённых схем, попавших в top-K           | Сравнение очередей          | Recall на редком классе                        |
| Лаг до подтверждения                                 | Средний и распределение     | Планирование горизонта                         |

## 7. Критерии остановки

1. Precision@K не выше baseline после 3 месяцев при одинаковом K.
2. Guardrail нарушен и не исправлен за 2 недели.
3. Комплаенс/DPO отзывает согласование.
4. Ключевые данные недоступны > 2 недель без обходного пути.

## 8. Связь с экономическим условием

Пороги успеха (10% / 5%) — это **минимум**, при котором пилот считается успешным. Но при этих порогах эффект = **6 480
000 ₽**, а TCO = **16 435 740 ₽**, ROI = **−60,6%**. Поэтому:

- Успех пилота — необходимое, но не достаточное условие для прода.
- Переход в прод — только при выполнении одного из условий ADR-002: пилот превышает 25% / 10–15%, или регуляторный
  риск ≥ 10 млн ₽, или отказ от найма 2–3 FTE.
