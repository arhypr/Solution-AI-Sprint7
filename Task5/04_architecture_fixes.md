# Правки архитектуры

Три блока: что должен был поймать мониторинг, какой регрессионный набор прогонять при смене модели/промпта, как
выкатывать и откатывать. Плюс петля данных для новых сегментов.

## 1. Мониторинг: что должен был поймать

### 1.1. Сегментный резолвер

Перед скорингом — детерминированный компонент `Segment Resolver`, который присваивает операции тег сегмента: `seller` /
`non_seller` / `unknown`. Признаки: ОКВЭД, контрагент из справочника площадок, паттерн текста. Это не модель, а
справочник + правило — дёшево, объяснимо, версионируется.

Тег используется:

- в мониторинге (разрез метрик);
- в регрессионном наборе (стратификация);
- в rollout (canary по сегментам);
- в fallback (если сегмент `unknown` или покрытие признаков низкое — ручной разбор).

### 1.2. Сегментно-осведомлённые метрики

Все ключевые метрики считаются **отдельно по сегментам**:

| Метрика                       | Что показывает                                        | Порог алерта                                    |
|-------------------------------|-------------------------------------------------------|-------------------------------------------------|
| precision@K по сегментам      | Качество ранжирования в каждом сегменте               | Падение > 5 п.п. vs baseline сегмента           |
| override rate по сегментам    | Как часто человек не соглашается с моделью            | Рост > 20% vs baseline сегмента                 |
| fallback rate по сегментам    | Доля кейсов, ушедших в фолбэк                         | Рост > 10 п.п. vs baseline                      |
| feature coverage по сегментам | Доля null/default/stale по history-признакам          | Падение покрытия ниже 80% для сегмента          |
| OOD score по сегментам        | Насколько сегмент далёк от обучения                   | Рост выше порога, откалиброванного на валидации |
| text OOV по сегментам         | Доля незнакомых токенов                               | Рост выше порога                                |
| rule firing rate по сегментам | Как часто правила срабатывают                         | Всплеск > 2× vs baseline сегмента               |
| **queue composition**         | Доля rule-driven vs model-driven в top-K по сегментам | Сдвиг доли rule-driven > 10 п.п.                |

### 1.3. Change-point detection

На каждую сегментную метрику — детектор изменения режима (CUSUM или Bayesian change-point). Он ловит не «метрика ниже
порога», а «метрика изменила поведение». Это позволяет увидеть деградацию раньше, чем она пробьёт статический порог.

### 1.4. Что запускает повторную проверку

- Change-point на precision@K любого сегмента.
- Рост queue composition (rule-driven доля) выше порога.
- Падение feature coverage ниже порога для сегмента.
- Рост OOD или text OOV выше порога.
- Рост override rate.

При срабатывании — автоматический тикет в разбор с приложенным срезом по сегменту.

Схема: `diagrams/02_segment_aware_monitoring.puml`.

## 2. Регрессионный набор при смене модели или промпта

### 2.1. Состав

Сегментно-стратифицированный набор:

| Страта                                                                                              | Минимум      | Что покрывает                     |
|-----------------------------------------------------------------------------------------------------|--------------|-----------------------------------|
| `non_seller` (старые клиенты)                                                                       | 200 операций | Базовое качество не должно падать |
| `seller` (новый сегмент)                                                                            | 200 операций | Качество в сегменте               |
| Edge cases: транзит, обнал, дробление                                                               | 100 операций | Классические схемы                |
| Edge cases: легитимные «подозрительные» паттерны (селлеры, благотворительность, зарплатные проекты) | 100 операций | Ложные срабатывания на легитимном |
| Текстовые вариации: новые формулировки                                                              | 100 операций | Text drift                        |
| Клиенты без истории                                                                                 | 50 операций  | Feature staleness                 |

Итого ≥ 750 операций с эталонной разметкой (из контрольной выборки Task2 + label audit Task5).

### 2.2. Метрики и гейты

| Метрика                         | Гейт                               |
|---------------------------------|------------------------------------|
| precision@K overall             | Не ниже предыдущей версии − 2 п.п. |
| precision@K по каждому сегменту | Не ниже предыдущей версии − 3 п.п. |
| feature coverage по сегментам   | Не ниже 80%                        |
| fallback rate                   | Не выше предыдущей версии + 5 п.п. |
| override rate                   | Не выше предыдущей версии + 10%    |
| rule firing rate                | Не выше 2× baseline                |

**Если новый сегмент не представлен в наборе** — модель не может быть выкачена на этот сегмент; для него остаётся
rules-only + ручной разбор до накопления данных.

### 2.3. Когда прогонять

- При каждой смене версии модели.
- При каждой смене правил (Rules Engine).
- При смене промпта (если LLM используется как вспомогательное звено).
- При смене справочников (сегменты, контрагенты, ОКВЭД).
- Перед каждым canary-шагом rollout.

## 3. Rollout и rollback

### 3.1. Схема выката

1. **Shadow mode.** Новая версия скорит весь трафик, но не влияет на очередь. Сравнение с текущей на регрессионном
   наборе и на живом трафике ≥ 2 недели. Если сегментные метрики не хуже гейтов — шаг 2.
2. **Canary 5%.** Новая версия обслуживает 5% трафика, стратифицированно по сегментам. Guardrails по сегментам
   проверяются ежедневно. Если OK ≥ 1 неделя — шаг 3.
3. **Canary 25%.** То же, ≥ 1 неделя.
4. **100%.** Полный выкат. Мониторинг продолжается.

### 3.2. Rollback

- **Feature flag на версию модели.** Переключение на предыдущую версию — один флаг, без редеплоя.
- **Автоматический rollback** при нарушении любого сегментного guardrail: precision@K сегмента −5 п.п., override rate
  +20%, rule firing rate 2×, feature coverage < 80%.
- **Аварийный режим:** rules-only. Если модель недоступна или откат не помогает — очередь строится только правилами и
  суммой, инцидент в мониторинг.
- **Постмортем** после каждого rollback: какая гипотеза не подтвердилась, что меняем в регрессионном наборе.

Схема: `diagrams/03_rollout_rollback.puml`.

## 4. Петля данных для новых сегментов

- **Контрольная выборка включает новые сегменты с первого дня.** Как только `Segment Resolver` начал тегировать
  `seller`, эти операции попадают в стратифицированную контрольную выборку.
- **Приоритет разметки:** новые сегменты размечаются первыми. Это дороже, но без этого модель никогда не выучит сегмент.
- **Триггер переобучения:** если покрытие сегмента в обучающих данных ниже порога (например, < 500 размеченных
  операций), переобучение не запускается — сначала сбор данных. Иначе модель выучит сегмент на шуме.
- **Явное решение по сегменту:** либо отдельная модель/правила, либо «не обслуживаем моделью, только правила и ручной
  разбор», либо «обслуживаем, но с пониженным приоритетом и обязательным подтверждением». Решение фиксируется в ADR и
  пересматривается при накоплении данных.

## 5. Что меняется в C4 из Task3

| Компонент                     | Изменение                                                                                                         |
|-------------------------------|-------------------------------------------------------------------------------------------------------------------|
| `Decision & Priority Service` | Добавляется `Segment Resolver` (детерминированный) перед скорингом; сегментный тег идёт в контракт и в мониторинг |
| `Monitoring & Audit`          | Добавляются сегментные метрики, change-point detection, queue composition                                         |
| `Model Registry`              | Добавляется регрессионный набор как артефакт, привязанный к версии модели                                         |
| `Training Pipeline`           | Добавляется проверка покрытия сегментов перед обучением                                                           |
| `Prioritized Queue`           | В контракт добавляется `segment` и `source` (rule-driven / model-driven)                                          |

## 6. Что это даёт

- Деградация в новом сегменте видна **в день появления сигнала**, а не через три месяца.
- Переобучение запускается **только когда есть данные**, а не «на всякий случай».
- Выкат новой версии не может незаметно ухудшить сегмент: регрессионный набор и canary по сегментам это блокируют.
- Откат — один флаг, автоматический по guardrail.
