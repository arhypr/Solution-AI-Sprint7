# Итоговый диагноз

## Что показывают дешёвые эксперименты

| Эксперимент            | Ожидаемый результат                                                                                                   | Что отсекает                                                       |
|------------------------|-----------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------|
| E1. Сегментный разрез  | Падение precision@K только в `seller`; в `non_seller` — стабильно                                                     | Системную деградацию (H8 для всех, H4 для всех)                    |
| E2. Покрытие признаков | У части селлеров высокая доля null/default по history-признакам (новые клиенты); у части — значения есть, но сдвинуты | Чистую H2 как единственную причину; оставляет H1+H2 как комбинацию |
| E3. OOD/PSI            | Высокий PSI по частоте операций, сумме, доле возвратов; умеренный OOD                                                 | Подтверждает H1                                                    |
| E4. OOV текста         | Высокий OOV по новым формулировкам, но не катастрофический                                                            | H3 как вторичный фактор, не основной                               |
| E5. Top-K по источнику | Доля rule-driven кейсов в top-K для селлеров выросла с ~20% до ~50%                                                   | Подтверждает H6 как усилитель                                      |
| E8. Контрфактическое   | Скоры старых клиентов не сдвинулись                                                                                   | Модель не «сломалась» системно                                     |
| E6. Label audit        | Большинство флагов селлеров — ложные (легитимные операции); подтверждённых новых схем мало                            | Подтверждает H4; H7 остаётся возможной, но не основной             |

## Диагноз

**Основная причина — H4: concept drift для нового сегмента.** Модель выучила, что «много мелких поступлений +
дробление + расчёты с множеством контрагентов» — признак схемы. Для селлеров маркетплейсов это нормальный профиль:
выплаты от площадки, возвраты, расчёты с самозанятыми. Связь «признаки → риск» изменилась: то, что было сигналом, стало
фоном.

**Усилитель — H6: rule interference.** Правила дробления и мелких поступлений массово срабатывают на селлерах. Они
поднимают в top-K кейсы, которые модель бы отранжировала низко. Очередь заполняется rule-driven кейсами, precision@K
падает даже там, где модель могла бы работать.

**Вторичный фактор — H3: text drift.** Новые формулировки назначения платежа не встречались в обучении. Это ухудшает
качество скоринга, но не является основной причиной: даже с идеальным текстом профиль селлеров остаётся «нетипичным» для
модели.

**Сопутствующий фактор — H2: feature staleness у части селлеров.** Новые клиенты без истории получают дефолтные значения
history-признаков. Это ухудшает качество для подгруппы, но не объясняет всю картину.

**Артефакт оценки — H5.** Precision@K падает частично потому, что изменилась базовая доля подтверждений и состав
очереди. Если считать precision@K только по model-driven кейсам, падение меньше. Это не отменяет H4, но означает, что
метрику нужно декомпозировать.

**H7 (адаптация мошенников) — возможна, но не подтверждена.** Без label audit нельзя сказать, есть ли в сегменте
реальные новые схемы. Если E6 покажет значимую долю подтверждённых новых схем — H7 добавляется как отдельная проблема,
требующая новой постановки, а не только переобучения.

**H1 и H8 — не основные.** Модель не «сломалась» (E8), pipeline не сломан (E7 чист). H1 присутствует как фон
(распределение сдвинуто), но это следствие H4, а не отдельная причина.

## Почему мониторинг не поймал

Три слепых зоны:

1. **Метрики агрегированы по всем сегментам.** Падение в одном сегменте «разбавлялось» стабильностью остальных.
   Деградация стала видна, только когда сегмент вырос до заметной доли потока.
2. **Состав очереди не отслеживался.** Рост доли rule-driven кейсов в top-K не был виден: смотрели на precision@K, а не
   на то, из чего состоит очередь.
3. **Покрытие признаков по сегментам не измерялось.** Доля null/default/stale считалась в целом, а не по сегментам.
   Проблема новых клиентов без истории была невидима.

## Что это означает для архитектуры

Модель не нужно «чинить» переобучением на старых данных — это ухудшит ситуацию. Нужно:

1. **Видеть сегменты** — сегментный резолвер и сегментный разрез метрик.
2. **Видеть состав очереди** — разрез top-K по источнику (правило vs модель).
3. **Видеть покрытие признаков** — аудит по сегментам.
4. **Управлять сегментами явно** — либо отдельная модель/правила для селлеров, либо явное решение «не обслуживаем
   сегмент моделью, только правилами и ручным разбором», пока не накоплены данные.
