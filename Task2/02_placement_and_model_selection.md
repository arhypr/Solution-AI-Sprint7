# Размещение, шортлист моделей и процедура приёмки

## 1. Жёсткие ограничения (отсекают варианты до сравнения)

1. **Банковская тайна и персональные данные.** Операции, счета, документы заявок, тексты обращений содержат защищённые
   сведения. Передача в публичный API без договора обработки и правового основания недопустима.
2. **Регуляторный контекст ПОД/ФТ.** Решение встраивается в правила внутреннего контроля; окончательное решение по
   операции принимает человек. Модель не может быть единственным основанием для блокировки или отказа.
3. **Право субъекта на возражение.** Решения, основанные исключительно на автоматизированной обработке и затрагивающие
   права субъекта, требуют установленных законом условий; для заёмщиков-ИП и поручителей-физлиц это уточняется юристами.
4. **Объяснимость для комплаенса.** Для флагмана нужна не только метрика, но и набор сработавших признаков, который
   сотрудник может проверить.
5. **Допустимость обработки в конкретном контуре** определяется комплаенсом, DPO и юристами; архитектор собирает вопросы
   и границы, но не выносит правовой вердикт.

**Практическое следствие:** публичный API как единственный контур для флагмана отсекается. Для №18 и №5 публичный API
допустим только с маскированием и после правового заключения; по умолчанию пилот идёт в контуре банка.

## 3. Шортлист моделей под выходной контракт

Шортлист собирается под конкретный выход, а не по публичному рейтингу.

### 3.1. Флагман: приоритизация очереди (выход — скор + top-K)

| Кандидат                                                                                 | Почему в шортлисте                                                                                                         | Ограничения                                                                                                         |
|------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| **Градиентный бустинг (XGBoost / CatBoost)** на табличных признаках и эмбеддингах текста | Сильный baseline для табличных данных, интерпретируем через SHAP, быстрый в проде, хорошо работает при дисбалансе классов. | Не использует структуру связей между клиентами и контрагентами.                                                     |
| **Графовая модель (GraphSAGE / GAT)** поверх графа «клиент — контрагент — операция»      | Транзит и дробление — это структурные паттерны; графовые модели улавливают их лучше табличных.                             | Дороже в разработке и эксплуатации, сложнее объяснять комплаенсу, чувствительна к качеству графа.                   |
| **Гибрид: правила + бустинг/графовый скор**                                              | Детерминированные правила отсекают известное, модель ранжирует остаток — это и есть целевая архитектура.                   | Требует настройки стыка правил и модели.                                                                            |
| **Изоляционный лес / unsupervised**                                                      | Не нужен эталон, может дать сигнал на непроверенной части.                                                                 | Не выдаёт вероятность схемы, только аномальность; использовать как вспомогательный признак, а не как основной скор. |

**Что не берём в шортлист:** чистый LLM как единственный скорер. Без эталона нельзя доказать, что он ловит схемы, а не
стиль текста; объяснимость для комплаенса недостаточна. LLM может быть вспомогательным звеном для эмбеддингов текста
назначения платежа.

### 3.2. №18: извлечение полей из документов

| Кандидат                                                                   | Почему в шортлисте                                                                                               | Ограничения                                                                                                                   |
|----------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------|
| **LayoutLMv3 / FinTableFormer-подобные layout-aware модели**               | Учитывают текст, layout и координаты; сильны на формах, счетах и выписках; предсказуемая стоимость инференса.    | Требуют OCR-пайплайна и разметки; на редких формах качество падает.                                                           |
| **Мультимодальная LLM (open-weight, в контуре)**                           | Хорошо работает на разнородных форматах без отдельной разметки под каждую форму; может сразу выдавать структуру. | Дороже на массовом потоке, сложнее контролировать галлюцинации; для пилота допустима как второй кандидат после layout-модели. |
| **Гибрид: layout-модель для полей + LLM для сложных/нетиповых документов** | Баланс стоимости и качества; LLM подключается только на low-confidence.                                          | Сложнее в эксплуатации.                                                                                                       |

### 3.3. №5: маршрутизация обращений

| Кандидат                                   | Почему в шортлисте                                                                                                                            | Ограничения                                                                                                                 |
|--------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|

## 4. Процедура окончательного выбора

### 4.1. Какие кандидаты остаются после отсечения

- Флагман: XGBoost/CatBoost, графовая модель, гибрид «правила + модель». Unsupervised — только как вспомогательный
  признак.
- №18: LayoutLMv3-класс, мультимодальная LLM в контуре, гибрид.
- №5: RuBERT, гибрид RuBERT + LLM. Чистый LLM на массовом потоке — только если пилот покажет, что разметки недостаточно
  и стоимость токенов приемлема.

### 4.2. Сценарии для приёмочного набора

| Инициатива | Сценарии                                                                                                                                                    | Сколько примеров                                                                                               |
|------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------|
| Флагман    | Транзит; обналичивание; дробление под пороги; нормальная операция с «подозрительным» текстом; операция из непроверенной части потока (контрольная выборка). | Не менее 500 операций на сценарий, из них контрольная выборка — не менее 20% для оценки на несмещённых данных. |
| №18        | Бухгалтерский баланс; отчёт о финансовых результатах; банковская выписка; скан плохого качества; документ с нестандартной формой.                           | Не менее 200 документов на тип; не менее 50 — low-quality.                                                     |
| №5         | Типовое обращение в один отдел; обращение, касающееся двух отделов; неоднозначная формулировка; новое обращение без истории.                                | Не менее 300 обращений на канал, из них не менее 50 — неоднозначные.                                           |

### 4.3. Приёмочные метрики и пороги

| Инициатива        | Метрика                                                                                                                                | Порог                                                                                        | Откуда порог                                                                                                                                                                   |
|-------------------|----------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Флагман           | **Precision@K** (доля подтверждённых схем в верхушке очереди) при K, равном пропускной способности службы (около 10 тыс. операций/мес) | Не ниже baseline-правил **и** не ниже согласованного с комплаенсом уровня                    | Порог задаётся не «красивым числом», а сравнением с текущим процессом и пропускной способностью. Дополнительно — **yield@K** и **recall на контрольной выборке**.[reference:3] |
| Флагман guardrail | Доля ложных блокировок и жалоб                                                                                                         | Не хуже текущей (около 600 приостановок/мес, 120 жалоб)                                      | Guardrail не должен ухудшаться, пока улучшается целевая метрика.                                                                                                               |
| №18               | Доля документов, в которых **все** обязательные поля извлечены верно (end-to-end accuracy)                                             | Не ниже согласованного с андеррайтингом уровня; ошибка на критическом поле — отдельный порог | Оценка по конечному результату, а не только по OCR.                                                                                                                            |
| №5                | macro-F1 и доля перемаршрутизаций                                                                                                      | macro-F1 не ниже 0.75 на приёмочном наборе; доля перемаршрутизаций не выше baseline          | Порог исходит из стоимости ошибки: неверный маршрут обратим, но задержка стоит денег.                                                                                          |

### 4.4. Что означает провал на сценарии

- **Флагман:** если precision@K на контрольной выборке не выше baseline-правил — модель воспроизводит существующее
  смещение и не даёт бизнес-эффекта; возвращаемся к данным и постановке, а не «улучшаем модель».
- **Флагман:** если на сценарии «дробление» модель систематически проседает, это не обязательно провал всей инициативы;
  возможно, нужен отдельный структурный признак или графовое звено.
- **№18:** если end-to-end accuracy ниже порога на массовом типе документа — пилот не масштабируем; если просадка только
  на редких формах — это ограничение охвата, а не провал.
- **№5:** если macro-F1 ниже порога, но top-3 покрывает большинство случаев — можно оставить top-3 с ручным выбором;
  если и top-3 плох — постановка требует multi-label или уточнения «правильного» отдела.

### 4.5. При каком результате решение меняется

- Если контрольная выборка покажет, что подтверждённых схем в непроверенной части **крайне мало**, приоритизация может
  не дать измеримого precision@K; тогда пересматриваем ценность инициативы, а не только модель.
- Если комплаенс/DPO не согласует обработку в выбранном контуре, размещение пересматривается до смены модели.
- Если стоимость LLM на массовом потоке окажется выше согласованного бюджета, для №5 и №18 переходим к fine-tuned
  моделям и гибриду.
